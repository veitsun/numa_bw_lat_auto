# NUMA Bandwidth & Latency Auto Benchmark (Slurm)

本项目提供一套 **基于 Slurm 的 NUMA 架构自动探测 + NUMA 带宽/延迟测试** 的一键化脚本，用于在多 NUMA node 服务器上系统性地测量：

- **CPU 位于某 NUMA node 时**
- **访问绑定到不同 NUMA node 的内存**
- 所对应的 **内存带宽（GiB/s）** 和 **访问延迟（ns）**

典型用途包括：
- 分析服务器 NUMA 拓扑与本地/远端访问差异
- 验证 NUMA 亲和性策略是否生效
- 为性能建模、调度策略或论文实验提供基础数据

---

## 1. 功能概述

该脚本完成以下工作流程：

1. **自动探测服务器 NUMA 架构**
   - NUMA node 数量
   - 每个 NUMA node 对应的 CPU 列表
2. **生成标准化 NUMA 拓扑描述文件**
3. **遍历所有 (cpu_node → mem_node) 组合**
4. 对每种组合执行：
   - 内存带宽测试（多线程、流式访问）
   - 内存延迟测试（随机指针追逐，抑制硬件预取）
5. **输出结构化 CSV 结果文件**
6. 所有步骤通过 **Slurm (`sbatch`) 在计算节点上自动完成**

## 3. 环境要求

### 必须条件
- Linux（x86_64），支持 NUMA
- 多 NUMA node 服务器（≥ 2）
- Slurm 调度系统
- gcc（支持 `-O2 -march=native -pthread`）
- 基本用户态工具：
  - `bash`, `awk`, `sed`, `sort`, `uniq`, `paste`
  - `lscpu`

### 权限说明
- **不需要 root 权限**
- **不依赖 libnuma**
- 使用 `mbind` 与 `sched_setaffinity` 的系统调用

## 4. 快速开始

### 4.1 一键提交

在项目根目录执行：

```bash
chmod +x submit_numa_sweep.sh
./submit_numa_sweep.sh
```

脚本会：
- 自动创建一个新的输出目录
- 使用 sbatch 提交 Slurm 作业
- 在计算节点上完成所有测试


### 4.2 自定义参数（推荐）

可通过环境变量控制测试参数：
```bash
SIZE_MB=2048 \
ITERS=60 \
BW_THREADS=8 \
STRIDE=4096 \
./submit_numa_sweep.sh
```

参数说明：

| 参数        | 含义                        	 | 默认值           |
| ----------- | ------------------------------- | -----------   |
| SIZE_MB     | 每次测试分配的内存大小（MB）       |  1024		   |
| ITERS       | 带宽测试循环次数                  |   50		     |
|BW_THREADS   | 带宽测试线程数（每个 NUMA node 内）|   4		      |
|STRIDE       |延迟测试 stride（字节）            |  4096		  |

SIZE_MB：分配的内存大小决定了测试覆盖的层级和结果稳定性
- 覆盖层级：小于或接近 L3 容量时，数据可能常驻缓存，带宽/延迟体现更多是缓存层；远大于缓存（几十 MB、几百 MB、GB 级）时，才主要测到 DRAM 与 NUMA 远/近节点差异。
- 噪声与时间：更大的分配会让一次遍历耗时更长，计时更稳定但整体测试时间增加；太小则跑得快但容易被调度抖动、预热效应影响。
- NUMA 绑定的有效性：分配并触页的区域越大，越能确保页确实绑定在目标 NUMA 节点上，不会只测到少量已在本地缓存的页。
- TLB/页表影响：更大区域会跨更多页，能体现页表/TLB 行为；小区域跨页少，对这些影响不敏感。


TIERS：带宽测试的循环次数，用来放大运行时间，降低噪声
- 每次循环会遍历一次分配的缓冲区。iters 越大，总读写的数据量越多，测量时间越长。
- 延长测量时间可以平均掉调度抖动、缓存冷暖等随机因素，得到更稳定的带宽值。
- 如果 iters 太小，测试很快结束，计时误差和系统背景干扰会让带宽结果波动较大；太大则耗时增加但精度收益递减。

BW_THREADS：决定带宽测试开启多少个工作线程
- 每个线程会：绑定到指定 CPU（来自 --cpulist 或主 CPU 号），拿到缓冲区自己的分块，按 64B 步长循环读出 64 位数据、做一次异或写回，重复 iters 次。
- 这样多个线程并行流式读写不同分块，提升总访问并行度，测得更接近多核下的内存带宽。
- 线程数太小可能无法打满内存通路；太大可能超出节点 CPU 数造成调度抢占。适当调大到能覆盖本节点核数或内存通道即可。


STRIDE：是延迟测试里每次跳转的字节间隔：随机置换的指针链按这个步长分布在缓冲区上，每次加载都跨越 stride 字节。控制测到的层级和干扰
- 小 stride（几十到几百字节）更容易命中同一/相邻 cache line，测到的更像 L1/L2 行为。
- stride≈cache line 或一页（64B–4KB）能让访问跨 cache line，避开预取，接近 L3/内存延迟。
- 更大 stride（多页）会让每次访问跳到不同页，放大 TLB/页表开销，更接近纯 DRAM 访问。
